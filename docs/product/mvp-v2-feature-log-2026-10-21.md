# Plan B MVP v2 feature log

**Status:** Implemented on 2026-10-21 for team review. Built with Claude Code assistance (see the [AI-use log](../team/ai-use-log.md)). No participant has tested v2, so nothing below is user evidence.

This log records what the [Plan B MVP](../../apps/plan-b-mvp/README.md) v2 builds from the "Re-evaluated ideas" section at the end of the [prototype ideas](../design/prototype_ideas.md), where each feature gets its data, and what remains untested. It extends the [MVP scope of 2026-10-20](mvp-scope-2026-10-20.md); the interview evidence behind the original scope is traced there. The re-evaluated ideas are the student's own design proposals, not participant findings, and this log does not add any interview evidence.

## Decisions and deviations

- **Stack:** The front end stays plain HTML, CSS and JavaScript with a Python standard-library server, with no build step and no new dependencies. Streamlit was considered, because the student's note allowed it, and rejected because it cannot reproduce Prototype 6's app look, page push transitions, bottom sheets and spring animations. The v1 files `live.js` and `live.css` were replaced by `app.js` and `app.css`. `demo.html`, `demo.js` and `styles.css` are unchanged.
- **Elevation source:** The idea expected elevation from the Routes API. The Routes API does not supply it, so the app samples walking-path coordinates and queries an elevation service. The Google Elevation API is not enabled on the team key, so Open-Meteo's free API is used and receives those sampled coordinates. If the team enables the Google Elevation API, it is used automatically.
- **Uber price:** The idea expected real Uber estimates. Uber's price-estimate API needs approved partner access, so the app opens an Uber deep link instead and does not display an Uber price. Rideshare cost is labelled unknown.
- **Parking cost:** Google does not provide parking prices or live availability. The app lists car parks and uses a "Typical parking cost" setting. Driving cost is marked incomplete when paid parking exists and no cost is set.
- **Flat public-transport fare:** Google returned no Translink fares in testing, so Settings has a flat fare used when none is returned. The default of $0.50 is an assumption that the team should check against current Translink fares.
- **Default destination wording:** The default destination text changed to "The University of Queensland, St Lucia QLD 4072" because Google placed the old wording about 1.5 km west of campus. The map shows where Google placed the destination so the traveller can check it.
- **Arrival-time fix:** Arrival times now use scheduled board and alight times, because Google's transit duration can exclude a long wait for a later service. v1 could under-state arrival time. Consecutive walking steps are merged into one "Walk about N min to a stop" step with turn-by-turn directions kept in the detail view, and duplicate transit routes are removed.
- **Scope shift:** The [MVP scope](mvp-scope-2026-10-20.md) listed live disruption detection and an embedded interactive map as "Will not have". Both are now partly implemented in v2 (Translink alerts and delays; Leaflet map). Vehicle tracking, booking, payment, accounts and background push notifications are still excluded.

## What was checked

- 82 offline unit tests in `test_live_routes.py`, `test_gtfs_rt.py` and `test_rides.py` pass without network calls, and cannot verify external data.
- On 2026-10-21 the app was driven end to end in headless Microsoft Edge with the team key: home, settings, Plan B search, detail sheet with map, next steps, trip logging, dashboard, ride board, panic mode, dark mode and regular trip mode rendered with no console errors.
- The Routes API and Places API (New) were checked as enabled on the team key (fuel prices and car parks returned for Brisbane). The Elevation API is not enabled.
- This is developer checking. No participant has tested v2, and no learning card or hypothesis decision should rely on it.

## Suggested next tests

These are tasks for the team to plan and record. They do not report results.

1. Agree owners and dates in the team's GitHub Project, then have a team member who did not build v2 review the code, this log and the README.
2. Compare Translink alerts shown by the app with Translink's own alerts page during a real disruption, and record any missed or wrongly matched line, especially for train lines.
3. Check the $0.50 flat fare, the CO2 factors and the Elevation fallback against current published sources, and decide whether to enable the Google Elevation API.
4. Run the existing three observed scenario tasks from the MVP scope with consenting participants, and add Panic mode as a fourth task: record time to a chosen option, assistance, whether the participant understands the recommendation and what they would check before travelling.
5. Test whether people understand "vs driving", the elevation labels and the parking flags, and whether hiding card fields in Settings reduces confusion.
6. Test the ride board with a small group on one local server, and decide with the team how safety, identity and moderation would have to work before any wider use.
7. Try the app on real phones and with keyboard and screen-reader use, and check reduced-motion behaviour.
8. Record any participant observations in approved de-identified interview records, using participant codes and documented consent, before any learning card is updated.
