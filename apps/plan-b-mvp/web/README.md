# Reroute web shell (Vite + React)

The React shell that owns the page frame, routing, page transitions, smooth scrolling and the DOM motion layer. The screens are either native React components (`src/screens/`) or the legacy `app.js` HTML builders, rendered through a bridge. There is no WebGL: no `three`, no canvas, no shader. Everything moves by sliding, fading and settling elements.

Stack: react 18, react-router-dom 6, framer-motion 11 (layout morphs and its spring generator only), lenis, @capacitor/haptics (native only). Elements move with Web Animations on `translate` / `opacity`, which the browser runs on its compositor thread.

## Develop and build

```bash
cd apps/plan-b-mvp/web
npm install
npm run build                 # -> web/dist (git-ignored)
VITE_SLOWMO=1 npm run build   # same, plus the slow-motion hook (see Choreography); never ship this build
```

- **Served by Flask:** `python server.py` (from `apps/plan-b-mvp`). If `web/dist/index.html` exists, Flask serves it for `/`, `/index.html`, `/terms`, `/privacy`, `/about`, and `/assets/*` (hashed, immutable). If `web/dist` is absent it serves the old `index.html`, so the plain app still works.
- **Hot reload:** run Flask on 8000 (`python server.py`), then `npm run dev` and open `http://127.0.0.1:5173`. If Flask is not on 8000: `FLASK_URL=http://127.0.0.1:8641 npm run dev` (also honoured by `vite preview`). On OneDrive paths the dev server can serve a stale module for several seconds after an edit; for visual checks prefer a build. Vite proxies `/api`, `/app.js`, `/offline.js`, `/app.css`, `/vendor`, icons and the manifest to Flask. `base` is `/`.
- Rebuild after changing anything in `web/src`; the service worker (`sw.js`, cache `planb-reroute-21`) precaches the hashed files it finds in the cached `/` page.

## Architecture

```
index.html -> src/main.jsx -> App.jsx
  <MotionLayer/>              DOM motion layer, mounted once (src/motion, below)
  <div id="app"> ... <main id="viewport">   static chrome the legacy code looks up by id
     <AppRoutes/>             BrowserRouter + LayoutGroup + AnimatePresence(mode="wait"), rendered once legacy scripts have loaded
```

- **Routing (`src/Routes.jsx`)**: only the legal pages have real paths (`/terms`, `/privacy`, `/about`); every other screen stays at `/`. The shown screen travels in `location.state = { screen, direction }`. Browser Back/Forward (POP) derives the screen from the path, as the legacy `popstate` handler did. `AnimatePresence mode="wait"` means a navigation is two beats: the old page's elements leave, then the new page mounts and its elements arrive (the hand-over between the beats is a main-thread step: the leaving animation finishing, then React mounting the next page). `Page.jsx` is the wrapper every screen goes through.
- **Smooth scroll (`src/smoothScroll.js`)**: Lenis on each page's `.scroll` element (not the window), re-bound when legacy `rerender()` replaces the node (`reroute:rerender` event). Measured scroll velocity (`motion/velocity.js`) tilts the scroll reveals.
- **Haptics (`src/haptics.js`)**: `tick, soft, thud, snap, error`. `@capacitor/haptics` when `window.Capacitor?.isNativePlatform()`, otherwise `navigator.vibrate`; silent when motion is reduced or unsupported. A page leaving is a `tick`, its entrance settling is a `snap`, pressing a button is a `tick` (motion layer), a card seating while scrolling is a `thud`, a menu or settings opening is `soft` and a sheet is `snap`.
- **Reduced motion**: `html[data-motion="reduced"]` or `prefers-reduced-motion` (unless `data-motion="full"`), including flipping either mid-session: pages swap instantly (no stagger, no splash, no travel), no haptics, no Lenis, the motion layer uninstalls and restores the DOM.

## Choreography (`src/choreography.js`)

One file holds the timing and travel every element transition uses (pages, side menu, Settings, sheets, launch splash), so they share one feel: everything eases out (`EASE`, never an ease-in), position slides and settles with a short spring (`spring()`: 0.4 s, bounce 0.12), elements arrive 30 ms apart (`STAGGER_IN`) and leave 20 ms apart (`STAGGER_OUT`, 120 ms each), capped (`CAP` 7 entering, `CAP_OUT` 5 leaving: the rest share the last delay and fade with the group, so a leaving page clears in about 200 ms and arrives in about 350 ms). All other durations are the `DUR` table; see "Motion principles and timings" below.

- **Direction** (`useDirection()`, `getDirection()`, `setDirection()`; set by the router before it renders): `forward` leaves left and arrives from the right, `back` is the reverse, `up` (sheet-like) leaves down and arrives from below, `down` leaves down and arrives from just above. `travel(direction, "in" | "out")` gives the displacement.
- **Element animations (`fx`, `slide`)**: every moving element is a Web Animation (`el.animate`) on the CSS `translate` and `opacity` properties only (never `transform`, which the scroll reveals and framer's layout morphs own, never a layout property). Both run on the compositor thread, so after the first frame a busy main thread (React commit, GC, a slow phone) cannot drop a frame. The arrival spring is sampled once into 21 keyframes (`IN_CURVE`, from framer's spring generator, cached per offset), the leaving ease-out into 13; animations use `fill: "both"`, so the first painted frame is already the start pose, and are cancelled when they finish (an arriving element's inline style is cleared, a leaving panel line keeps its end pose inline, a leaving page holds it with `fill` until it is unmounted: framer's projection rewrites inline opacity on shared elements). `stop()` keeps what is on screen (`commitStyles`) before cancelling, so an interrupted animation retargets from where it is. Everything is registered with the motion layer, so Reduce motion mid-flight cancels it and restores the DOM. Past the cap an element shares the last delay; elements outside the viewport are not animated at all (nothing to see, the scroll reveals own them).
- **What moves on a page**: native screens mark their staggered elements `data-item` (`<Item>` and `<Shared>` in `shared.jsx`; `Rise` and `Island` the same), in DOM order; legacy HTML screens animate the direct children of their header, `.scroll` and footer and the map screens' loose blocks. Items nested inside another item are skipped. There are no framer variants any more.
- **Page lifecycle (`Page.jsx`)**: `usePresence` keeps the old page mounted until its exit has finished, with a watchdog (`watchdog()`, 600 ms) that force-completes a stuck exit; an interrupted exit (browser Back/Forward mid-transition) re-enters instead of deadlocking. The exit and the entrance both start in a layout effect, in the same task as the DOM commit. A tick fires as the exit starts and a snap when the entrance settles, which is also when `pageSettled()` lets the legacy side accept the next navigation (a backstop timer does it too, and immediately under reduced motion). Nothing the first frame does not need runs before it: legacy `pageMounted` only sets the current page and `inert`, and its focus, map mounting and chart binding (`lateMount` in `app.js`) run after the first frame (or earlier, if `pageSettled` / `rerender` get there first); Lenis is attached after the first frame; the motion layer's block sweep and ambient scan wait for an idle moment.
- **Slow motion for inspection**: in dev, or in a build made with `VITE_SLOWMO=1`, `window.__slowmo = 6` multiplies every duration, delay and spring by 6 so a frame can be captured mid-flight. Production builds contain no such code.
- **Scroll reveals** (`motion/scroll3d.js`) use `settle(k)`, the same spring as a pure function of scroll progress, so a block slides in from alternating sides and settles with the same overshoot as the page elements, still scrubbed by scroll.

### Shared layout (`src/shared.jsx`)

Elements that persist across screens carry a framer-motion `layoutId` (the router is a `LayoutGroup`), so they physically morph instead of leaving and re-entering: `impact` (home Impact button <-> dashboard lead figure), `nav-back`, `nav-home` and `title` (the large page title, position only).

Rules: (1) a shared element is exempt from the stagger **only when the screen being navigated to / from has its counterpart** (`hasShared(screen, id)` in `shared.jsx`: the screen must be native, and its markup must contain the element; for `impact` that is the home Impact button, or the dashboard lead figure, which exists only once a trip is logged). Then it morphs and the elements around it stagger. Otherwise nothing could morph, so it is an ordinary item: it slides and fades with the direction of travel, in DOM order, with the same easing and stagger as its neighbours (the Impact button leaves with the header row going to Weather, Results, Journey or an empty dashboard). Page.jsx skips the exempt ones; the router (`Routes.jsx`) tells `shared.jsx` where the previous and next screen are (`setNav`). (2) A shared element that has no counterpart gets a fresh layoutId namespace (`impact~7`), because framer keeps the last box of a removed layoutId node and would morph an unrelated new node out of it. (3) A container that holds a shared element is not itself animated (it would carry the element away); its children are staggered individually instead. `legacyNode()` applies the rules when legacy HTML becomes React (`screens/home/tree.jsx`, `screens/trip/LegacyTree.jsx`); the hand-written screens (`Navbar`, weather, legal) apply them by hand. Legacy innerHTML screens (panic, nav, offline-area) cannot carry a `layoutId`, so their Back/Home slide with the rest, and so do the shared elements of the screen before or after them. With `mode="wait"` the old page is gone before the new one mounts; framer keeps the old shared node's last box and the new node morphs from it, so the Impact button stays in place while everything else leaves and then grows into the lead figure. The morph itself is a main-thread layout animation (small: one button, one figure).

## Motion principles and timings

Rules applied (after Emil Kowalski's design-engineering notes): animate only what the user benefits from seeing, and less the more often they do it; ease-out only (a custom quint, never `ease-in`); leaving is faster than arriving; feedback under 160 ms and everything else under about 350 ms; press 0.97, never scale from 0 (0.9-0.95 plus opacity); origin from the trigger; transform and opacity only; interruptible (CSS transitions and springs retarget, no restarting keyframes on things that re-render); stagger 20-30 ms, capped; reduced motion removes movement. The vocabulary lives in `choreography.js` (`EASE`, `DUR`, `spring()`, `MORPH()`, `LAYOUT`, `STAGGER_*`, `CAP*`); new code imports it instead of writing numbers.

| Interaction | Timing | Why |
| --- | --- | --- |
| Screen change, exit | 120 ms per element, 20 ms stagger, cap 5 (about 200 ms total), ease-out; Web Animations, compositor | Fast exit: the user has already decided |
| Screen change, entry | spring 400 ms bounce 0.12 (sampled to 21 keyframes), opacity 200 ms, 30 ms stagger, cap 7 (last starts at 180 ms); Web Animations, compositor | The cascade reads as one gesture; late elements no longer trail |
| Layout morph (Impact <-> figure, Back, title) | spring 450 ms bounce 0.08 | Rare, spatially meaningful, calm |
| Press / release | 140 ms / 160 ms to scale 0.97, ease-out; Web Animations on `scale` | Immediate acknowledgement; release retargets from the current value |
| Hover lift (fine mouse only) | 2 px, 150 ms | Touch never hovers |
| Side menu / Settings / sheet panel | open 220 ms (drawer curve), close 300 ms (`--ease-close`, a gentle ease-out whose first 10 % of the time covers 16 % of the distance); scrim fades out over the same 300 ms; lines stagger in 30 ms (cap 9 / 7 / 6) and out 14 ms top first, 160 ms each, so the last is gone at 272 ms, just before the panel | A close that starts at full speed read as abrupt; the lines never outlast the panel. Pressing the menu button mid-close turns the same panel (and its lines) round from where it is |
| Profile menu | open spring 360 ms from scale 0.9 out of the avatar, close 200 ms to 0.95 (items 14 ms apart); reopening mid-close retargets; opacity + transform only (the old diagonal clip-path reveal was main-thread paint and was dropped) | Origin-aware; was 0.7 |
| Dialog | open 200-220 ms from scale 0.95, close 140 ms | Asymmetric |
| Skeleton to content | 240 ms fade and 6 px rise, 30 ms stagger | Hides the swap |
| Toast, autocomplete list, banners | 160-220 ms ease-out | Occasional |
| Autocomplete rows | none | Re-rendered on every keystroke |
| Field focus | none | Frequent, no information |
| Cards/List toggle thumb, switches | 200 ms, `--ease-spring` (2 % overshoot) | State change |
| Refresh button | 700 ms linear rotation while loading | Constant motion; faster reads as faster |
| Ambient loops | 3.6-7 s, rotation up to 4 deg, scale up to 3 %, glow up to 0.6; paused off-screen, in hidden tabs and with reduced motion | Calm background life |
| Splash | the mark draws, leaves at about 680 ms, and the first screen cascades in | Rare, authored |
| Scroll reveals (`scroll3d.js`) | unchanged | Scrubbed by scroll, signed off |

`settle(k)` in `choreography.js` is a fixed spring curve used only by the scroll reveals; it is deliberately independent of `spring()`, so changing the page spring never moves the scroll ranges. Pages, panel lines, the profile menu, press feedback, the splash and the skeleton cross-fade are Web Animations on compositor-friendly properties (see "Element animations"); the drawers, dialogs and ambient loops are CSS and always were. What still runs on the main thread: the layout morphs (`layoutId`), the scroll reveals (scrubbed by scroll), the busy-button loader (an SVG path) and the hand-over between a page leaving and the next one mounting (React commit: one frame of about 24 ms at 4x CPU throttle, up to 56 ms for the Weather page; the picture does not move for that frame). Measured in headless Chrome with the harnesses below; not measured on a real phone.

## Motion layer (`src/motion/`)

One `MotionLayer` (mounted in `App.jsx`) owns every DOM-level effect. It uses delegated pointer/focus listeners on `document` plus one `MutationObserver` on `#viewport`, so it treats legacy HTML-string screens and native React screens identically. It animates DOM nodes with Web Animations (`fx` / `slide` in `choreography.js`; framer's `animate` only remains for the busy-button loader) and never touches React state. Its block sweep and ambient scan run when the browser is idle, not in the frame that mounted a page.

| File | What it does |
| --- | --- |
| `MotionLayer.jsx` | Installs/uninstalls everything. Reduced motion (system preference or `data-motion`, including flipping mid-session) stops every animation, removes every inline style the layer wrote (`fm.js` keeps the registry), and removes the `html.fm` class and `data-fm` markers; turning it off installs the layer again. |
| `micro.js` | Press sinks to 0.97 (140 ms) and releases in 160 ms, both on `EASE` (no overshoot); hover lift only for a fine mouse. No animation on field focus (it fails the frequency test). Drives the CSS individual `scale` / `translate` properties with Web Animations (a press holds its pose inline until the release), never `transform`. `motion.css` neutralises the CSS `:active` transform while `html.fm` is set so the two do not stack. |
| `panels.js` | Menu / settings / sheet backdrops (class `open` toggled by `app.js`): the panel slides in CSS as before and the lines inside it slide in one after another from the panel's own side (menu from the left, line by line; Settings from the right; sheets from below) with the choreography spring and stagger (`slide`, Web Animations). Closing eases the panel out in CSS (300 ms) while the lines slide out top first (14 ms apart) and finish just before it; reopening mid-close eases the lines back from where they are; a panel being dragged shut is left alone. Soft haptic (menu, settings) or snap (sheet). Busy buttons (`button.is-loading`) get the route-bend loader. A skeleton replaced by content cross-fades over 240 ms. |
| `ambient.js` | Adds `.amb-off` to scroll blocks that leave the viewport (IntersectionObserver); `ambient.css` pauses every loop inside them. |
| `scroll3d.js` | Never touches a block while its page is changing: registration, re-measure and re-assert are deferred to `reroute:settled` (dispatched by `Page.jsx` when the entrance ends; before that clearing the inline transform / opacity snapped blocks back to rest mid-flight). Every direct child block of `.scroll` / `.sheet-scroll` (and `.chart-card`) below the fold slides in from alternating sides and settles (`settle`), scrubbed by scroll progress (reverses on scroll back; ranges are clamped to the scrollable distance so the last block always seats). Blocks tilt (rotateX, max 7 deg) with scroll velocity and ease flat. A card seating gives `thud`. Chart bars grow (`scaleY`), `.hero-art` / `.kpi.lead` drift up and dim, `.kpi b` figures count up once when 30% visible. Opt out with `data-fm-off`; opt a custom native block in via `data-fm-reveal`. Blocks already on screen are staggered by the page choreography, not here. |
| `launch.js` | Splash sequence: the first page is mounted but hidden under the splash; once the app is ready and the mark has drawn, the mark slides away with the page-leave motion, the backdrop fades and the first screen's elements stagger in (the `launched` promise gates `Page.jsx`). Reduced motion: no splash. |
| `velocity.js` | The scroll velocity motion value (fed by Lenis and native touch scroll). |
| `motion.css` | `html.fm`-scoped overrides (CSS entrances/transitions that would fight per-frame writes, the CSS `:active` transform) and the switch-off of app.css's timed splash exit and of its `rise` / `fbIn` CSS entrances on the blocks of a page (a CSS animation overrides the inline transform / opacity the page choreography writes). |

Cost model: transform / opacity / `translate` / `scale` for feedback; layout is read only when something new is registered or the viewport resizes (batched, writes after reads, one reflow); the press / hover / focus handlers and the scroll handler perform no layout reads. Nothing runs at rest: the scroll flush is scheduled only while scrolling or while the tilt eases out, Lenis (no `autoRaf`) loops only while it glides after a wheel event. Everything pauses on `visibilitychange: hidden`.

## Manual smoke test (no browser driver is installed in this repo, so there is no `scripts/smoke.mjs`)

1. `VITE_SLOWMO=1 npm run build`, start Flask (`HOST=127.0.0.1 PORT=8641 python server.py`) and open it at 390x844 with service workers unregistered and caches cleared. Expect: splash, mark slides away, first screen's elements stagger in, no console errors, no `canvas` in the DOM.
2. Set `window.__slowmo = 40`, tap the Impact button: the page's elements slide left one after another, the Impact button stays, then the dashboard mounts and its elements arrive from the right while the lead figure grows out of the button (it needs at least one logged trip in `localStorage` `planb.trips`). Repeat with Back, the menu items, browser Back/Forward and rapid taps (nothing may stay inert or half-hidden).
3. Open the menu on home: the lines slide in from the left one by one. Close it: the panel eases out over about 300 ms while the lines slide back top first and are gone just before it, the scrim fading with it; press the menu button again halfway and the panel turns round without a jump. Settings slides from the right, sheets rise.
4. Scroll the home screen: blocks slide in from alternating sides and settle, tilt with speed, one `thud` (`navigator.vibrate(16)`) as cards seat.
5. `document.documentElement.dataset.motion = "reduced"`: pages swap instantly, `html.fm` removed, no press scale, no haptics. Set `"full"` again: everything is back.

## Measuring motion (`web/scripts/`)

`scripts/motion-bench.js` is one `async (page) => result` function for playwright (the MCP `browser_run_code_unsafe`, or any runner). It switches demo mode on, answers `/api/plan` from `scripts/plan.fixture.json` (made by `python web/scripts/make-plan-fixture.py` from the test fakes) and patches `/api/status` to `live_available`, so no Google API is called. For each of home<->results/dashboard/weather/journey, journey->results, results->next, panic, nav, menu open/close, settings, sheet and profile menu it runs twice: pass 1 records `requestAnimationFrame` deltas, `longtask`, `layout-shift` and the time `pageMounted` / `rerender` took (no sampling, so it is clean); pass 2 samples `getComputedStyle` opacity / translate / transform of the moving elements after every frame (in a task posted from rAF, so it sees what was painted) and flags any direction reversal over 2.5 px / 0.08 opacity as a snap-back or flash. Settings: `globalThis.BENCH_CFG = { cpu: 4, only: "menu", raw: "panel", base: "http://127.0.0.1:9031/" }` before evaluating it (`cpu` is `Emulation.setCPUThrottlingRate`, `raw` returns the raw samples of matching elements). Serve the file with any static server and `eval` it, since the MCP sandbox has no `fs`. A frame over 20 ms at 1x or any flagged path is a regression.

`scripts/motion-perf.js` (same conventions) has two modes. `mode: "impact"` (with `seed: true` to log a trip first, so the dashboard has a lead figure) samples the Impact button / lead figure after every frame for home <-> results / weather / journey / dashboard / panic and reports opacity and position reversals (none allowed). `mode: "busy"` is the off-main-thread check: `busy: "freeze", freezeAt: "mount"` blocks the main thread for 300 ms starting 100 ms after the next page is put in the DOM, records the screen with CDP `Page.startScreencast` (frames come from the compositor), diffs them in a second tab and reports `inFreeze`, the number of pictures that still changed during the block. A plain CSS transform animation (the control row) gives 6 to 8; main-thread animation gave 1 to 4; the compositor-driven pages give 6 to 7. Without `freeze` it blocks 30 ms every 100 ms. Do not leave its CDP session open: a running screencast slows the tab for every later measurement (the script detaches it). Serve the scripts folder (`python -m http.server 9102`) and `eval` the scripts from a one-line wrapper, since the MCP sandbox has no `fs`. Headless Chrome shares one process between tabs on the same site, so run one measurement at a time.

## The legacy bridge

`app.js` and `offline.js` are loaded as classic scripts by `legacyLoader.js` after the shell exists. `app.js` checks `window.RerouteBridge` (created in `src/bridge.js`, before it loads):

| Direction | API |
| --- | --- |
| legacy -> React | `RerouteBridge.navigate(screen, direction, syncUrl)`, `RerouteBridge.isNative(screen)`, `RerouteBridge.register({ rerender, pageMounted, pageSettled })` |
| React -> legacy | `RerouteBridge.legacy.pageMounted(el, screen)`, `pageSettled()`; globals `window.RerouteLegacy = { SCREENS, state, navigate, goBack, rerender, enhanceClear, pageClass, isTransitioning }` |

Legacy `navigate()` still does all state work (stack, sheets, menus, nav/panic/weather setup), then hands the DOM swap and URL change to React; React mounts a `.page` section whose HTML is `SCREENS[name]()` once the previous page has finished leaving, calls `pageMounted` (which sets `currentPage`, inert handling, focus, maps, charts) and, when the entrance stagger ends, `pageSettled` (clears `transitioning`, resizes and cleans maps). While the old page is still leaving, legacy `rerender()` does nothing (`currentPage.dataset.screen !== state.screen`), and a browser Back/Forward that arrives mid-transition waits for it to settle before the legacy state catches up with the address. `rerender()` keeps rewriting `currentPage.innerHTML` in place and fires `reroute:rerender`. Without `window.RerouteBridge` (plain `index.html`) `app.js` swaps pages itself as before. `motion.js` and the GSAP vendor files belong to the plain `index.html` only; the shell does not load them (everything they did lives in `src/motion` and `src/choreography.js`).

## Porting a screen to native React

1. Create `src/screens/<name>.screen.jsx` whose default export is the component, e.g. `dashboard.screen.jsx`. The part before `.screen.` is the route name: `home, journey, results, next, panic, nav, dashboard, rides, weather, offline-area, terms, privacy, sources`. (Or set `Component.screenName`.)
2. That is all. `src/screens/index.js` collects every `*.screen.{js,jsx}` with `import.meta.glob`, so the registry `screens` (`{ [name]: Component }`) needs no edit and parallel screens never conflict. The router prefers a registered screen over `LegacyScreen`.
3. The component renders the page body only; the shell supplies the `.page` section, the enter/exit stagger root, Lenis on `.scroll` and `pageMounted`. To take part in the page transition, render the direct children of the navbar and of `.scroll` as `<Item tag index={i}>` (any `motion.*` tag, see Choreography) and anything that persists across screens as `<Shared id=...>`; for legacy markup let `legacyNode` (`shared.jsx`) do it. Use the same markup classes (`.scroll`, `.eyebrow`, ...) so `app.css` applies. Legacy `rerender()` does not rewrite native pages; it fires `reroute:rerender` with `detail.native = true`, so a native screen can re-read `RerouteLegacy.state` on that event.
4. Native pages still use legacy actions: keep `data-action="..."` attributes and the global click delegation keeps working.
